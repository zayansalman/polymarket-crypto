# Lessons

## A "structural cost" argument is a hypothesis until you measure the counterfactual (2026-08-14, #182)
**Pattern:** Asked whether Polymarket account `@mayormamdani` could be copy-traded, I argued no on structure: he is a maker (40.3% of fills at implied fee rate ~0, bimodal against 35.3% at ~0.07), so a copier must cross and pay `0.07*p*(1-p)`. From one live book I computed a 2.75c/share disadvantage (1.00c spread + 1.75c fee) against his ~0.55c/leg edge and called it "5x the edge against you, before any latency." The operator pushed back twice. Building the mirror and settling 8 real fills: **his PnL +$24.79, copying him +$22.81 — 92% captured, 1.56c/share actual slippage.** The reasoning failed because it priced the copy against a *static* book. Between his fill and the copy the price moves, and he is often filling dips that revert — so the copier frequently gets a BETTER price than he did (`bnb Up: him 0.687, us 0.538`), and on his losers enters so cheap the loss barely lands (`sol Up: him 0.240 -> -$4.80, us 0.011 -> -$0.21`).
**Why:** A per-trade cost term (spread, fee) is a *lower bound on one leg of the comparison*, not the comparison. The copier's entry price is `target_price + drift`, and drift on a 5-minute crypto binary is +-20-40c — an order of magnitude larger than the spread and roughly symmetric, so it dominates and does not systematically favour either side. Reasoning from the cost term alone silently assumes drift is zero.
**How to apply:** When arguing something cannot work because of a structural cost, (1) state the cost as a fraction of the *total* variance in the outcome — if a competing term is 10x larger and mean-zero, the cost term does not decide the sign; (2) build the cheapest possible measurement of the actual counterfactual before asserting a conclusion, especially when the operator has asked for that thing specifically; (3) note that "he is a maker, you would be a taker" remains TRUE and was not the error — the error was pricing what that asymmetry costs. Same session, same failure mode twice: I also benchmarked his 68% stranded-leg loss rate against a 50% null when the legs averaged 0.374 (fair loss rate ~63%); against the correct price-implied null, z = -1.36, n=35 — no effect. **Both errors pointed toward "don't build it."** Ties to [[screen-population-trap]] and the FDR lesson: pick the null from the data-generating process, not from a round number.

## A book-vs-book gap of ≈ constant × n is a missing cost term, not alpha (2026-07-02)
**Pattern:** Live "beat" its own shadow counterfactual by +$26.55 on 240 identical windows at identical entry prices (+$0.11/window). I briefly read it as execution alpha / a fee-free venue before checking venue cashflows: the gap was almost exactly the taker fee shadow subtracts (~$0.087/trade) that the live books silently omitted (`record_settlement` booked `held*(payout−entry)` gross, live.py). Venue truth (Data API usdcSize): bot-era PnL −$17.24 vs booked −$8.01 — the books flattered losses 2×, and the daily loss-halt tracked the flattered number.
**Why:** Two books can only diverge by a near-constant per-trade amount when one carries a per-trade term the other doesn't (fee, spread convention, rounding). Real alpha is noisy; accounting artifacts are flat.
**How to apply:** Before interpreting ANY book-vs-book difference, (1) divide the gap by n and compare to every known per-trade cost; (2) validate one book against actual venue cash movements (`usdcSize` on the Data API: buys pay `price×size + 0.07·p·(1−p)·size` when they cross at placement, maker fills and redemptions are fee-free); (3) fix the book at the source, don't reconcile forever (#133). Ties to [[model-calibration-near-null]], screen-population-trap.

## Absence from a filtered venue snapshot is not absence on the venue (2026-07-02)
**Pattern:** I declared stranded position 1768 a phantom because its token was missing from the Data API `/positions` list. The positions list is structurally loss-biased and incomplete (unredeemed tokens only; winners drop out on redemption). The `/activity` stream + the order's own journalled placement response (`status='matched'`, tx hash) proved the entry filled AND won — auto-redeemed +$2.41 thirty seconds after the bot crashed.
**Why:** Snapshot endpoints answer "what is held now", not "what happened". Proving a negative needs the event stream (trades/redemptions) or the order record, not a state snapshot.
**How to apply:** To establish that an order/position never existed, check the activity/trade stream for the window AND the journalled placement response — never conclude from a positions/state list. The journal's `details_json.response` is venue truth captured at submit time and survives CLOB order pruning (that's what the #132 boot heal now uses).

## FDR/permutation-test a sliced finding BEFORE presenting it as real (2026-06-23)
**Pattern:** I presented a "mid-volatility sweet spot" regime finding as "doubly supported (literature + our ledger)" and let the user start designing a regime panel + auto-selection around it. A max-rigor re-review demolished the ledger half: 0/12 vol×strategy cells significant, 0/12 survive Benjamini-Hochberg FDR, and a 5000× within-model permutation test could not reject the null (mid-premium p=0.21, total-spread p=0.65). My eye-catching v0 triple (lo −0.03 / mid +0.69 / hi −0.09) wasn't even reproducible under 5 alternative vol measures. Across the whole session ~95 cell-tests gave 7 nominal p<0.05 vs 4.8 expected by chance (P≥7 = 0.20) — indistinguishable from the global null. The only FDR "survivors" were degenerate `late_convergence_v3` slices that mechanically excise its rare −4.5 loss tail (artifact, not edge).
**Why:** Slicing ~370 windows × 6 models × several regime axes is dozens of hypotheses; the most extreme cell ALWAYS looks like signal. With per-trade SD≈2.44, detecting a +0.1/+0.2/+0.3 edge needs ~4,671/1,168/519 trades (~90/22/10 days live). At per-cell n=15–90 we are nowhere near powered — exactly the prior edge-archaeology null.
**How to apply:** Before calling ANY sliced/conditional result real: (1) run FDR (Benjamini-Hochberg) + a within-model permutation test across ALL cells, report how many survive; (2) flag degenerate cells whose SD ≪ the model's full-sample SD or that exclude a known fat-tail (favorite-soak models manufacture fake t-stats this way); (3) state the MDE/power for the cell n. A regime panel is fine as DESCRIPTIVE monitoring, but "strategy X wins in regime Y" is noise until it clears FDR on out-of-sample data. Ties to edge-archaeology-null, [[live-edge-unproven]].

## Verify operational claims against current code, and don't quote point-in-time dollars from a live-growing DB (2026-06-23)
**Pattern:** Same re-review caught three avoidable errors: (a) I claimed "live is gated to 05–12 UTC so deep-night can't trade" — FALSE; the trading-window gate was ripped out in commit `b88f034`; live trades 24/7. I inferred a live gate from *historical* `btc_live_orders` BLOCKED "outside trading window" rows that no longer correspond to any code. (b) My live-PnL dollar figures (−$2 to −$4, ROI −0.3%, a "−$12" settlement-path number) were stale/wrong — the DB grew and the live total is now slightly POSITIVE (+$2 to +$10); the −$12 was a mis-read of `btc_live_orders.notional_usd`, which on `intent='SETTLEMENT'` rows is *signed realized PnL*, not a position notional. (c) Shadow PnL is net of a fee = 0.07·shares·p·(1−p) (~3.5% of cost at p=0.5), not a flat 7% of cost.
**Why:** Historical journal rows reflect past config, not current behavior. A live-writing SQLite ledger makes any hard-coded count/dollar a moving target. Field semantics differ by row type.
**How to apply:** For any "the bot does X" claim, grep the CURRENT code/config, don't infer from old journal rows. For any ledger number, snapshot the DB (or state `as of <date>, n=<N>`) and recompute per session — never carry a dollar figure forward. Confirm a field's meaning per row-type before summing it. The QUALITATIVE conclusion (live flat, indistinguishable from breakeven, underpowered; t=0.26, CI ±~$80) survived; only the hard numbers were wrong.

## In-memory trade state is a cache; reconcile it to the authoritative ledger (2026-06-17, #91)
**Pattern:** Live trading silently stopped — the BLOCKED panel showed "an open position/order already exists (max 1)" on every entry, while the position ledger was flat AND Polymarket showed the last position fully bought+sold. The blotter and the venue *agreed* (both flat); only the live executor's in-memory `_position_open` / `_entry_order_id` were stranded `True`. Two causes: (1) a fully-MATCHED entry kept its order id, so `entry_order_resting` lied (a filled order isn't resting — Polymarket: "matched orders can't be canceled"); (2) under a rapid stop/start storm (~10 BOOT_RECONCILE in 20 min) an interrupted shutdown left the flag set, and boot reconcile only syncs *from* an open ledger row, never heals a phantom when the ledger is already flat.
**Why:** The singleton gate keyed off a mutable in-memory cache with no path to re-derive it from the source of truth once it diverged. A cache that can outlive its truth WILL diverge under restarts/crashes and then block forever.
**How to apply:** When an in-memory flag gates the money path, give it a heal path against the authoritative store, and find the SAFE invariant that lets you clear without risk — here, a live ledger row is closed only after a *confirmed venue flatten*, so **ledger-flat ⟹ venue-flat**, making it safe to clear a phantom when the ledger shows zero open rows. Heal on the hot path (next tick), not just at boot. Debug from real state first: the `btc_live_orders` journal `details_json` (cancel responses) + the actual Polymarket history pinned the root cause faster than reading code. See [[project-btc-5m-polymarket-bot]].

## Respect the existing UI architecture for dashboard work (2026-06-16)
**Pattern:** When adding any dashboard UI, conform to the established panel architecture instead of bolting on a bespoke surface:
- Pure `render(...) -> str` panel module in `btc_5m_fv/ops/dashboard/panels/` (no DB access in the panel).
- Read data in `ems.py` (or `panels/_data.py`) and pass it in; `ems.py` orchestrates and composes the grid.
- Reuse the theme CSS vocabulary (`card`, `card-h`, `de-kv`, `gr-btn`/`btn-ok`, `pill`, `mono`, `win`) and add any new classes in `static/style.css` matching the Bloomberg-EMS variables.
- Controls POST to a `/api/...` endpoint and call the existing global `refreshAll()`; persist to the `config` table; re-read per tick (mirror `refresh_overrides` / `set_paper_bypass_loss_halt`).
**Why:** Keeps the dashboard consistent, testable, and SSE-refreshable; avoids one-off patterns that drift from the rest of the EMS.
**How to apply:** Before building dashboard UI, read `panels/__init__.py`, `_shared.py`, an existing panel (e.g. `guardrails.py`), `ems.py`, `dashboard.js`, and `style.css`; then slot the new piece into those seams.

## Scope tightly; don't over-build (2026-06-16)
**Pattern:** Initial ask sounded like "max trade size + singleton/multiple mode + max positions"; after planning the full multi-position LiveExecutor refactor, the operator narrowed it to "just make max trade size settable in the UI, leave singleton."
**Why:** The money-path refactor (scalar→map LiveExecutor) was large and risky; the operator's real need was a single runtime knob.
**How to apply:** When a request spans a cheap change and an expensive architectural one, confirm scope before building the expensive part. A short clarifying question up front avoided a large unwanted diff here.

## A "smaller clip" can be an *unplaceable* clip — validate against the venue minimum (2026-06-17, #85)
**Pattern:** The #50 max-trade-size feature let the operator set any cap `0 < v ≤ 1000`, reasoning a value below the min-trade size "just gives a smaller fixed clip." It doesn't: a $1 cap at favourites (price ≥ 0.50) sizes every order below Polymarket's 5-share minimum, so the live executor blocked 100% of entries. Live trading was dead for a full session before anyone noticed.
**Why:** A per-trade *ceiling* below the sizing *floor* (`BTC_PAPER_MIN_TRADE_USD`) inverts the range; `notional_from_confidence` then pins every order to the floor → sub-minimum. The UI showed "min $5.00" but only as cosmetic text — no boundary actually enforced it (endpoint, HTML `min`, and gate read all let $1 through).
**How to apply:** Any operator-settable risk/sizing knob must be validated against the *venue* constraint it feeds, not just a sanity range. Enforce at every boundary (endpoint reject + gate read + UI widget), and make stored-state auto-heal so an already-persisted bad value doesn't keep biting after the fix ships. When a UI shows a "min/max", wire it to real validation — never leave it as a hint. See [[project-btc-5m-polymarket-bot]].

## Don't over-correct a "too small" bug into a blunt restriction (2026-06-17, #87)
**Pattern:** Fixing #85 (a $1 clip blocked all trades), I slammed a flat $5 floor on the size knob. The operator pushed back: "did you create a $5 minimum? I want to control my trade sizes." The flat floor removed legitimate control — Polymarket's real limit is **5 shares/order**, which at ≥0.50 favourites costs only **$2.50–$5** depending on price, NOT a flat $5. A blunt dollar floor forbade valid sub-$5 clips.
**Why:** I corrected from one extreme (any value, including unplaceable $1) to another (no value below $5) without modelling the actual constraint shape: a per-order, price-dependent share minimum. The fix that preserves operator control is to **bump sub-minimum orders up to the exact venue minimum** (cap becomes a target, not a hard ceiling), so any positive clip places.
**How to apply:** When a value is "too small/large," derive the TRUE constraint (here: shares × price, not a dollar) and prefer the option that keeps the operator in control (auto-bump/clamp-to-valid) over a blunt reject. For a real knob with a genuine trade-off (hard ceiling + partial-block vs soft cap + always-place), ASK the operator — it's their risk control. See [[project-btc-5m-polymarket-bot]] and [[feedback_cac_is_steering_not_scoreboard]].

## Never rank strategies on an aggregate that can hide a regime break (2026-06-22)
**Pattern:** Asked "how are the strats doing," I crowned `down_skeptic_v4` as the best shadow model off its 5-day total (+$42) and even a 48h cut (+$16). The operator pushed back: v4 had "a massive fallout in the last 24h" and I'd ignored `down_skeptic_drift_v6`. Decomposing by day exposed it: v4 was −$11.90 *today* with a **−$26.69 intraday drawdown** (peak +4.48 @00:26 → trough −22.22 @06:45), driven by its Down bets getting run over in an up-trending regime (today's Down side: 24% win, −$39). The aggregate completely smoothed this over.
**Why:** A multi-day sum averages across regimes. A model whose edge is regime-dependent (here: a Down-skeptic that bleeds when BTC trends up) looks great in aggregate while actively blowing up. Ranking on the sum is the screen-population-trap in the time dimension.
**How to apply:** When reporting strategy performance, ALWAYS show the recent decomposition (daily PnL + intraday max-drawdown), not just the total — especially before calling anything "best." For a *new* variant (v6 had 7 trades / 2h), do a **shared-window head-to-head** vs the incumbent before crediting it: v6's apparent +$10.69 lead was 100% survivorship — on all 7 windows it shared with v4 they made the *identical* PnL; v6 simply wasn't alive for v4's morning drawdown. Tie back to drift-cross-market-falsified (drift adds no edge → expect v6≈v4 at scale) and screen-population-trap.

## Attribute strategy PnL by the SIDE BET, never by realized outcome (2026-06-22)
**Pattern:** Building the regime view, I split down_skeptic_v4's PnL by realized window outcome — Up-windows +$125.8, Down-windows −$84.2 — and concluded it was a "disguised long with a regime-flip, not a real edge." Adversarial verification (and my own re-check) killed that: attributed by the side ACTUALLY BET, BOTH legs are net positive — Down-bet leg +$22.4 @65% win (n=43), Up-bet leg +$19.1 @59% (n=128). The short leg is its *better* one. The +125/−80 outcome split was a pure mechanical artifact of holding a 75%-long book; any model that bets Up 75% of the time shows +PnL on Up-outcomes and −PnL on Down-outcomes regardless of skill.
**Why:** Splitting by realized outcome conflates the book's directional tilt with edge. It fabricates a fake "directional disguise" for any non-50/50 book. The only attribution that measures skill is per-side expectancy/win-rate of the side the model chose.
**How to apply:** When asking "is this strat just long/short in disguise," group by `side` (the bet), compute each leg's win-rate and net PnL. Both legs positive = genuine two-sided edge. Never use `outcome` for attribution. AND: small-sample regime sign-flips are noise — for the most robust model, 0/10 regime-bucket 95% CIs excluded zero over 5 days; "regime-robust" means sign-consistent, not proven. Also: a single 5m day's swing isn't a regime — v4 lost −$15 on 06-22 while BTC rose +1.45%, driven by its win-rate dropping to 46% in chop, not by direction. See [[feedback_decompose_recent_trend_not_aggregate]], model-calibration-near-null, edge-archaeology-null (night 00-08 UTC is the one consistent regime: v4/v5 make ~all PnL in the day, bleed slightly at night).

## Commit incrementally — uncommitted work can be silently discarded (2026-06-17, #89)
**Pattern:** Mid-implementation of #89 (a multi-file feature), an external `git checkout develop` ran and discarded all my uncommitted edits + the branch checkout (reflog HEAD@{0} confirmed; the `.claude/settings.json` hooks only run gen_docs, so a hook wasn't the cause). I lost ~5 gate.py edits and had to redo them.
**Why:** Uncommitted working-tree changes don't survive a branch switch + discard. On a repo where something (another session, a scheduled task, or the operator) may run git commands between turns, holding a large uncommitted diff is fragile.
**How to apply:** On multi-file changes, COMMIT AFTER EACH LOGICAL CHUNK to the feature branch (gate → commit, sizing → commit, endpoint → commit, UI → commit). Committed work survives a checkout; only the current chunk is ever at risk. Verify edits actually landed (grep) after a "success" if anything seems off — a success message from Edit doesn't guarantee the change persisted if the tree is later reverted. See [[project-btc-5m-polymarket-bot]].
